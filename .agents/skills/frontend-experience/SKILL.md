# 콘텐츠 중심의 프런트엔드 경험

이 사용자의 기준은 **풍부한 인터랙션**과 **AI 티가 나지 않는 디자인**이다. 효과의 개수나 라이브러리 목록이 아니라 콘텐츠에 맞는 구성, 입력에 대한 반응, 실제 화면의 완성도로 판단한다.

## 1. 구현 전에 방향을 만든다

목적·대상·실제 콘텐츠·핵심 행동·브랜드 자산·기존 스택을 확인한다. 이미 정한 것을 다시 묻지 않는다. 중요한 정보만 질문하고, 판단을 맡겼다면 근거를 갖고 선택한다.

Build Web Apps의 `frontend-app-builder`가 설치되어 있으면 그 스킬을 읽고 콘셉트 → 디자인 시스템 → 구현 → 브라우저 비교 흐름을 따른다. 이 스킬은 사용자 취향을 그 흐름에 반영하는 지침이다. 별도의 커스텀 디자인 에이전트를 기본으로 끼워 넣지 않는다. 해당 플러그인이 없어도 사용할 수 있는 디자인 도구로 콘셉트를 만들되, 사용자가 그 플러그인을 명시했다면 사용 불가 사실과 대안을 먼저 알린다.

코드를 작성하기 전에 작업 폴더의 `design/`에 다음을 남긴다. 문서 수와 파일명은 프로젝트에 맞춰 간결하게 선택한다.

- **콘셉트**: 다루는 콘텐츠가 왜 이 타이포그래피·색·공간·이미지 구도를 요구하는지, 페이지의 첫인상과 전체 흐름.
- **시각 근거**: 주요 섹션/상태를 구현할 수 있을 만큼 읽기 쉬운 콘셉트. 긴 페이지를 작은 히어로 시안 하나로 대신하지 않는다. 이미지 생성 결과의 글자·UI를 통째로 배경에 굽지 않는다.
- **인터랙션 맵**: 주요 섹션별 `콘텐츠 / 입력 / 반응 / 모바일·키보드 대안 / 움직임 감소 / 검증 방법`. 구현할 수 없는 효과나 미확정 자산은 명시한다.

사용자가 시안 검토 후 진행을 요청했다면 그 승인을 기다린다. 구현까지 맡겼다면 콘셉트를 먼저 보여주고 현재 권한 안에서 진행한다. 이미 채택한 콘셉트를 구현 중 임의로 다른 디자인으로 바꾸지 않는다.

## 2. 상투적인 선택을 걷어낸다

- 본문·UI는 **Pretendard**가 기본 선호다. 실제 폰트 로딩과 한글 줄바꿈을 확인한다. 제목은 콘텐츠·브랜드에 맞는 서체, 굵기, 자간으로 결정한다. 세리프를 분위기용 기본값으로 넣지 않으며, 특정 글꼴을 모든 브랜드에 강제하지 않는다.
- 화살표는 다음/이전·이동 방향 등 의미가 있을 때 사용한다. 모든 링크와 버튼에 같은 장식 화살표를 덧붙이지 않는다.
- 반복 카드와 같은 좌우 분할을 페이지 전체에 적용하지 않는다. 실제 콘텐츠의 중요도에 따라 사진·타이포그래피·목록·표·공간·여백의 비중을 바꾸고 하나의 시스템으로 연결한다. 카드가 필요한 제품 UI까지 금지하지 않는다.
- 더미 수치·무의미한 배지·아이콘 줄·장식용 영어로 빈 공간을 채우지 않는다. 같은 기능의 버튼과 상태 표시는 위치·크기·피드백을 일관되게 유지한다.

## 3. 인터랙션을 페이지의 일부로 설계한다

히어로 뒤에도 경험이 이어져야 한다. 제목·본문·이미지의 순차 등장, 스크롤 진행에 따른 장면 변화, 사진의 포인터 반응, 탐색·선택의 클릭 피드백, 드래그 관성처럼 **콘텐츠 자체**의 반응을 조합한다. 모든 섹션을 같은 fade-up으로 끝내거나, 장식 루프만 돌리고 실제 조작을 방치하지 않는다.

인터랙션 맵에 주요 섹션의 역할을 모두 적는다. 반응이 필요한 곳과 읽기에 집중하는 구간을 구분하고, 재사용 가능한 모션 언어 안에서 변주한다. 인터랙션 수에 할당량을 두거나 매번 새로운 효과를 발명할 필요는 없다.

스크롤 중심의 랜딩·프로세스에는 부드러운 스크롤을 기본 후보로 검토한다. Lenis/ScrollSmoother는 현재 환경과 실제 스크롤 루트에 맞을 때 선택한다. 앵커·뒤로 가기·중첩 스크롤·모달·모바일 터치·움직임 감소가 정상이어야 한다. 네이티브 스크롤을 선택했다면 그 이유를 짧게 남긴다.

GSAP/ScrollTrigger는 스크럽·핀·연속 타임라인에, CSS/IntersectionObserver/Web Animations는 적합한 가벼운 반응에 사용할 수 있다. AOS/Swiper도 목적에 맞으면 사용한다. **Three.js는 콘텐츠를 공간·입체·재질·회전으로 다루는 것이 도움이 될 때** 선택한다. 캐릭터·3D 로고·마우스 반응을 모든 사이트에 강제하지 않는다. 라이브러리를 써야 검증 PASS가 된다고 판단하지 않는다.

구현과 검증의 세부 기준은 [모션·입력·성능](references/motion-and-input.md)을 읽는다. 프로세스 페이지를 요청받았다면 [프로세스 페이지](references/process-pages.md)도 읽는다.

## 4. 콘셉트와 실제 화면을 함께 검증한다

사용 가능한 Browser/내장 브라우저에서 실제 페이지를 연다. 사용할 수 없거나 불안정하면 이유를 기록하고 Playwright로 검증한다. 새 플러그인 설치는 현재 도구로 해결되지 않을 때만 제안한다.

브라우저의 실제 크기와 비교 상태를 고정하고 채택한 콘셉트와 최신 캡처를 직접 본다. `view_image`가 있으면 두 이미지 모두 확인한다. 폰트·줄바꿈·이미지 크롭·섹션 간격·요소 위치·색·겹침을 비교하고 큰 차이부터 수정한다. 생성 시안과 런타임 캡처를 같은 것으로 소개하지 않는다.

데스크톱·태블릿·모바일에서 다음을 확인한다.

- 첫 화면과 아래 섹션의 실제 렌더, 오버플로·텍스트/버튼 가림·누락 자산·콘솔 오류.
- 인터랙션 맵의 핵심 흐름: 스크롤, hover/focus, 클릭, 드래그, 앵커 이동, 터치 대안. 입력 전후의 실제 상태를 확인한다.
- 최초 진입·반복 진입·구간 이동에서 모션이 보이는지와 입력이 끊기지 않는지. 장치·뷰포트·관측 방법을 적고 측정하지 않은 고정 fps를 주장하지 않는다.
- 움직임 감소에서 콘텐츠와 기능이 유지되는지, 스크롤을 왕복했을 때 등장/해제가 자연스러운지.

간단한 검증 기록에 **콘셉트 근거 / 실제 결과 / 수정 또는 의도한 차이 / 미검증 영역**을 남긴다. 빌드 성공, 작은 픽셀 차이, 효과의 개수로 디자인 완성을 대신하지 않는다. 수정 가능한 큰 차이와 조작 오류를 해결한 다음 완료를 보고한다.

## 퍼블리싱 도구와 연결

고정된 화면 상태를 정밀하게 맞출 때는 `reference-publish`의 측정·Visual/Geometry/Responsive QA를 사용한다. 실제 상태와 모션 검증은 `interaction-ready` 및 관련 패턴 스킬을 선택한다. 이들은 검증 수단이며 새 디자인 방향을 정하는 권위가 아니다.

`work/interaction-plan.json`은 자동 QA용 DOM 계약이다. 구현 전 인터랙션 맵을 대신하지 않는다. `--mode design`을 사용할 때는 작성한 `work/motion-language.json`을 `--motion-language`로 명시한다. DOM 분석이나 고정 기본 효과를 창작 콘셉트로 취급하지 않는다. WebGL 등 자동 검증 밖의 경험은 브라우저에서 직접 검증하고 한계를 분리한다. 기존 퍼블리싱 Stop Hook을 우회하려고 미지원 기능을 자동 PASS로 표시하지 않는다.

## 전달

실제 작업 경로, 사용한 스킬, 검증한 흐름과 남은 한계를 간결하게 알린다. 바이브 코딩 프로젝트의 공개 README를 요청받으면 제작 계기·콘셉트·스택·핵심 경험·관람/프로세스 링크를 중심으로 쓴다. 대화 경위와 내부 변경 로그를 앞세우지 않고 생성/외부 자산의 출처는 사실대로 표시한다. 공개나 배포는 현재 요청 범위에서만 수행한다.
